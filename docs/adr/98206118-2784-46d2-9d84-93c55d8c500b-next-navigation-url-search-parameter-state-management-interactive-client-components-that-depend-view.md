# next/navigation URL Search Parameter State Management: Interactive Client Components That Depend View

Status: proposed
Date: 2025-05-15
Deciders: Detection Pipeline (automated)

## Scope Paths

Applies to:
- `app/search/**`
- `components/cart/**`
- `components/layout/**`
- `components/product/**`
- `lib/shopify/**`

## Context

- Catalog presentation and product selection interfaces require state persistence across page reloads and deep linking
- Multiple client rendering components across search, catalog filtering, product variant selection, and gallery views require read and write access to query parameter state
- Centralizing query parameter synchronization through next/navigation enables bookmarkable views without introducing external client-side caching dependencies
- Server-side and client-side boundaries consume query parameters to coordinate variant lookup and catalog filtering

## Problem Statement

Managing client-side catalog filtering, search query input, gallery image selection, and product variant options in isolated in-memory component state causes state loss on browser refresh and breaks URL shareability. The application requires a unified state access convention that treats URL search parameters as the primary query state datastore across client components.

## Decision

1. MUST: Interactive client components that depend on view filtering, sorting, variant selection, or pagination state MUST source and synchronize that state through next/navigation URL search parameter access APIs rather than unpersisted client memory stores.

## Policy Block

- MUST Interactive client components that depend on view filtering, sorting, variant selection, or pagination state MUST source and synchronize that state through next/navigation URL search parameter access APIs rather than unpersisted client memory stores.

In scope:
- Interactive client components managing filter, sort, search, variant, or view selection parameters
- Catalog and search interfaces that require deep linking and bookmark preservation

Out of scope:
- Sensitive transactional state such as authentication credentials or payment tokens
- High-frequency ephemeral UI interactions such as hover states, animations, or cursor tracking

## Rationale

- Utilizing next/navigation search parameter APIs as the authoritative query state datastore guarantees that all catalog filter and selection states remain serializable and shareable
- Eliminates synchronization drift between URL location bars and internal component state by deriving UI presentations directly from searchParams.get
- Adheres to standard web navigation primitives without requiring heavier client-side global state management libraries

## Consequences

Positive:
- Filter, search, and variant selection states are natively shareable through URL links and preserved across page refreshes
- Browser navigation history controls back and forward traversal across selection states without custom undo stacks
- Reduces client bundle overhead by relying on framework-native navigation utilities rather than third-party state caches

Negative:
- State payloads are constrained by URL length limitations and string serialization formats
- Rapid parameter updates trigger navigation transitions that must be debounced to prevent history stack inflation

## Alternatives

- In-memory client state management via component state or context providers (rejected)
  Rejected because: In-memory state does not persist across browser reloads, prevents link sharing, and requires custom persistence layers
  When valid: Transient UI interactions that do not represent catalog selection or bookmarkable view state
- Client-side storage through browser web storage APIs (rejected)
  Rejected because: Web storage is scoped to the local device and browser session, preventing cross-user link sharing
  When valid: User preferences that should persist across multiple sessions without appearing in shared URLs

## Risks

- Excessive navigation history entries generated by high-frequency query parameter mutations
  Mitigation: Replace history entries or debounce rapid input mutations when modifying search parameter values
  Owner: engineering team
- Unsanitized or invalid query parameter values causing variant lookup failures or runtime exceptions
  Mitigation: Enforce domain validation and fallback handling on all parameter values extracted through search parameter readers
  Owner: engineering team
